图 1　一屏 = 一个框架 + 6 个位置

single　只有一个占位者。再注册一个就是替换。
keyed　可以注册多个，按 key 选一个显示。
list　可以注册多个，全部同时显示。

插件之间的第一种关系：位置（拼界面）

  • 插件写 ctx.slots.inject('sidebar', …)：等这个位置被声明了，才注册进去。
  • 位置被卸载，注册自动撤销。
  • 插件之间不互相 import 组件。
例：packages/client/ui-sidebar/src/client/index.ts:88

插件之间的第二种关系：服务（讲依赖）

  • 关掉 ui-layout：24 个插件等不到 layout 服务，停在 pending。
  • 关掉 ui-sidebar-right：11 个插件等不到它的服务。
  • 卡住的里面有 7 个必需插件之一（如 ui-chat、ui-sidebar），页面拒绝启动；否则只打警告。
必需名单：packages/client/web/src/boot-client.ts:25-33，拒绝启动：同文件 :128

记一句：界面是"拼"出来的。ui-layout 只画格子，格子里是谁、有没有人，由插件自己决定；少了某个插件，依赖它的插件会停住，而不是报错崩掉。

图 2　数据分三路来

判断一份数据走哪一路，只问一个问题：它拿到之后还会不会自己变？

浏览器
Host（本机 127.0.0.1:3080）
1拿代码
读 HTML 里的 window.__DSH_BOOT__，知道要加载哪些插件，再去下载。
GET / GET /plugins/??a,b,c… 多个插件合并成一次下载
插件图 + 插件代码
只在打开页面时拿一次。
2一问一答
读配置和目录：模型、凭据、skill、预设。
第 1 级的 session/prompt 也走这一路。
HTTP POST /api/<ns>/<method> 问一次，答一次，结束
Remote 方法
不会自己变的东西，拿一次就够。
3订阅
会话、工作区这类随时会变的状态。浏览器不轮询，等 Host 推。
WebSocket /api/remote.mux 只有一条连接，上面跑多条逻辑流
持续推送
帧：{type, streamId, endpoint, payload}
type 是 open / item / cancel。
这一条 WebSocket 上，页面打开时开了 7 条逻辑流：
workspace/follow工作区与会话列表
session/control所有会话的摘要
session/follow当前会话的日志
job/list后台任务
account/watch账号
remoteAccess/follow远程访问
$events事件通道，带 ready 信号（见图 3）
每条流都是同一个节奏： 首帧：全量（baseline 或 snapshot） → 增量 → 增量 → …

记一句：不会变的用 HTTP 问一次；会变的在 WebSocket 上订阅，先收一份全量，之后只收变化。

图 3　为什么要"先订阅增量，再拿全量"

假设页面加载过程中，恰好有一件事 X 发生了（比如某个会话跑完了）。两种顺序的结果不一样。

dsh 的顺序：先订阅，再拿全量

X 不会丢：它要么已经在全量里，要么从增量通道到达。

反过来：先拿全量，再订阅

X 丢了：界面停在旧状态，直到下次刷新。
连接就绪后重开 control 流：packages/api/session-controller/src/client/index.ts:131-137（control.restart()）

记一句：先把"听变化"的通道接好，再去拿当前状态。两步之间发生的事才不会漏。

盖住图，自己答一遍

1. 想加一个全局提示条，应该注册到哪个位置？为什么不是 main？

shell.overlay。它是 list，加一项不影响别人。main 是 keyed，一次只显示一个 key，注册进去只有切到你的 key 时才看得到。

2. 模型列表走 HTTP，会话列表走 WebSocket，为什么不一样？

模型列表拿到后不会自己变，问一次就够。会话列表随时会变（新建、跑完、改名），所以要订阅，由 Host 推。

3. 关掉 ui-sidebar-right，页面会白屏吗？

不会。依赖它的 11 个插件停在 pending，但它们都不在 7 个必需插件里，所以只打警告，页面照常启动，只是没有右栏。

4.（还没学，留着）图 3 里 X 可能既在全量里、又从增量通道到达。客户端收到两次怎么办？

这个问题第 0 级没有回答。学到第 1 级的 1.5（刷新后的 baseline 和 revision）时回来填。
