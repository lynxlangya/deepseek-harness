图 2　放大 agent-loop：一轮对话里发生什么

图 1 里紫色那一块的内部。一轮（turn）从领到输入开始，到不再欠任何工作结束；一步（step）是一次模型请求加它调用的工具。

turn/start
一轮开始
领取输入
从 inbox 取出排队的消息；快照这一刻的模型选择；组装提示词片段和工具 schema
agent/pre-step
插件可以接纳、改写或拒绝这条输入。被拒绝就直接关闭这一轮
一步（step），可以重复
step/start
一步开始
system/messageuser/message
系统提示词和你的消息到这里才写进日志，然后从日志推导出要发给模型的历史
llm/stream
经适配器把请求发给模型。插件可以在这里包一层
agent/assistant-stream
start、chunk…、end。只在进程内存里，屏幕上逐字出现的就是它
assistant/messageassistant/attempt
成功就把整段流压成一条 message；失败、重试、取消记成 attempt，不进模型历史
tool/call
模型要调的每个工具各记一条
tools/pre-executetools/executetools/post-execute
执行前把关 → 真正执行 → 执行后处理。谁在把关，留给 2.2
tool/result
每个工具的结果各记一条
step/end
一步结束
↺ 工具结果还要交给模型，或者又来了新输入 → 再来一步
agent/turn-stopping
收尾前问一圈插件（serial 事件，没有 next()）
turn/end
一轮结束

黑底 持久会话事件

写进 session.vN.jsonl。刷新、重启后还在，历史靠它们重建。

绿虚线 瞬态事件

只在 Host 进程内存里。进程在这一步结算前被强杀，这段流就没了。

紫框 waterfall 扩展点

插件可以拦截的地方，像中间件：监听器必须调 next() 才往下传，不调就是截断。

为什么这么分

实时显示要快，所以 chunk 不落盘；能不能恢复只看持久事件，所以每一步结束时把整段流压进一条 message。

图 3　贯穿全图的三条规矩

图 1 里每一块都遵守这三条。看不懂某块代码时，先问它在这三条里扮演什么。

① 一切都是插件

模型适配器、工具注册表、会话日志、连 agent-loop 本身，都是 Cordis 插件。没有需要打补丁的内核。

插件做三件事：提供服务（ctx.xxx）、收发事件、做可撤销的注册。插件卸载时，它注册的东西自动撤销。

所以扩展 dsh = 再挂一个插件；改行为 = 用 patch 换掉某个插件的配置。

② 模型可见 ⟺ 已记录

发给模型的每一个请求，都必须能从会话日志重建出来。想让模型多看到一样东西，就得先有一种会话事件来记它。

例：你在 1.1 看到的 clientTimeZone 没放在请求头里，而是跟着消息写进日志，因为模型会看到"用户那边几点"。

③ 一项能力 = 三个角色

接口、实现、使用者分开，换掉实现就能换整个产品的行为。

fs
接口←fs-local
实现·tool-fs
给模型用的工具
把文件和进程的实现指向远程沙箱，bash、终端、LSP 就一起搬过去了，工具不用改。
事件的三个域是什么什么时候用
会话事件追加到日志的持久事实：turn/*、step/*、user/message、assistant/message、tool/*这件事刷新后还得在
Agent 事件agent/*，带着正在运行的 Agent：inbox、步骤、请求、续跑想观察或拦截进行中的工作
能力事件fs/*、tools/*、telemetry/*想给某项能力加策略，又不碰循环
