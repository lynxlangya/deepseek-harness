# dsh 学习路线：从 Web 界面往里学

> 方法沿用 pi 的学法：一课只做一个界面操作，回答一个问题，最多读一两个函数。
> 行号基于本地 `feat/learn`（2026-11-09，`0.2.2-rc.1`），dsh 迭代很快，对不上时搜函数名。

## 定位：为什么先学 dsh，和 pi 的关系

- dsh 已在生产使用，学到的东西直接用在迭代里，性价比最高。
- dsh 很大：约 379 个包、约 120 万行 TS。所以**不要通读**，只追界面上看得见的链路，其余先当黑盒。
- 和 pi 的关系：dsh 只在 [`llm-pi-ai`](../packages/llm/llm-pi-ai) 里用到 `pi-ai`，而且默认是休眠的（[base 组合包](../packages/bundle/base/cordis.patch.yml) 第 128 行的注释）。生产默认走自研的 [`llm-deepseek`](../packages/llm/llm-deepseek)。Agent 循环、会话、扩展都是 dsh 自己的。pi 里学到的"流式事件、usage、abort"这些概念能迁移，具体代码不能。

## 一个概念先搞懂：Cordis（10 分钟）

dsh 的每个部分都是 Cordis 插件，包括 agent loop 本身。前端类比：

| 你熟悉的 | dsh 里对应的 |
|---|---|
| 依赖注入 / React Context | `ctx.<key>` 服务，如 `ctx.llm`、`ctx.tools`、`ctx.sessions` |
| `useEffect` 返回清理函数 | `ctx.effect()`，插件卸载时自动撤销注册 |
| Koa / Express 中间件 | `waterfall` 事件，监听器必须调 `next()` 才往下传 |
| `addEventListener` | `ctx.on()` 和 `emit` |
| webpack 配置合并 | profile + 组合包 + `cordis.patch.yml` 按层叠加 |
| Redux action 日志 | Session 事件日志（`turn/start`、`assistant/message`……） |

先读 [Cordis 入门](../docs/cordis-primer.zh.md)（45 行），再读 [架构](../docs/architecture.zh.md) 的"轮次流程"一节。[Cordis 教程](../docs/cordis-tutorial/index.zh.md) 留到第 4 级写插件时再做。

## 准备：用独立的 DSH_HOME 跑源码

**注意**：`~/.dsh` 是你生产在用的数据目录（里面有 `sessions`、`merine-identity`、`llm-deepseek` 等）。源码版本可能比你装的版本新，会话格式迁移会写新文件。学习时用一个单独的目录，不碰生产数据：

```bash
cd /Users/langya/Documents/CodeHub/ai/deepseek-harness
DSH_HOME=~/.dsh-learn pnpm run dev:web
```

- 首次会先跑 `build:artifacts`，会比较慢；之后改源码会自动重建，浏览器收到 `rebuilt` 后刷新。
- 模型 key：在仓库根目录建 `.env` 写 `DEEPSEEK_API_KEY=...`（`.env` 已被 gitignore），或在 Web 的模型设置页里配。
- 看当前机器到底挂了哪些插件：`DSH_HOME=~/.dsh-learn pnpm dsh --profile web --dump-config`。

2026-11-09 实测：`DSH_HOME=~/.dsh-learn pnpm run dev:web` 可跑，`--dump-config` 可用；服务默认在 `127.0.0.1:3080`。

## 主线：在输入框发一句话，到屏幕出字

```
① 输入框提交        packages/client/ui-conversation/src/client/service.ts:234  sendSession
                    ↓  :309  session.prompt(content, mode, signal, requestId)
② Client model      packages/api/session-controller/src/client/sessions/session.ts:271
                    ↓  this.remote.session.prompt(...)  ── HTTP POST /api/session/prompt（DevTools Fetch/XHR）──
③ Host 接收         packages/api/session-controller/src/index.ts:467  @Remote('prompt')，记下调用来源
                    ↓  :491  this.commands.prompt(request, source)
                    commands.ts:321  prompt
                    ↓  校验附件、图片能力，:374  agent.followup(message)  放进 inbox
④ Agent 循环        packages/core/agent-loop/src/agent.ts
                    :297  agent/pre-step（waterfall，可改写或拒绝这条输入）
                    :336  turn/start 写进会话日志
                    :361  step/start
                    ↓  组装系统提示词 + 工具 schema，经 llm/stream waterfall 发请求
⑤ 模型适配器        packages/llm/llm-deepseek/src/adapter.ts:65  generate
                    ↓  fetch，accept: text/event-stream
⑥ SSE 解析          packages/llm/llm-deepseek/src/sse.ts:13  parseSse → StreamChunk
                    ↑  ─────────── 回程 ───────────
⑦ 实时推送          agent.ts:486  emit('agent/assistant-stream', { frame })
⑧ Host 转发         packages/api/session-controller/src/assistant-stream.ts  SessionAssistantStreamAccumulator
                    ↓  session/follow 逻辑流 ── WebSocket /api/remote.mux（DevTools WS）──
⑨ Client 窗口       session.ts 维护事件窗口；live chunk 和持久事件在 ui-conversation 里关联
⑩ 渲染              packages/client/ui-chat/src/client/conversation-nodes/assistant.ts → React
```

要点（来自 [架构](../docs/architecture.zh.md#turn-flow) 和 [Web Client](../docs/subsystems/web-client.zh.md)）：

- 屏幕上逐字出现的是**瞬态** `agent/assistant-stream` chunk；一步结束时整段流被压缩进**持久**的 `assistant/message`。刷新页面后，历史从持久事件重建，不靠 token 行。
- **模型可见 ⟺ 已记录**：发给模型的每个请求都能从会话日志重建。这是 dsh 的核心规矩，调试时先看日志。
- **去程和回程走不同通道**：一问一答的 Remote 调用（如 prompt）走 HTTP POST `/api/<namespace>/<method>`；持续推送的状态走唯一一条 WebSocket `/api/remote.mux`，上面多路复用多条逻辑流，帧格式是 `{type: open|item|cancel, streamId, endpoint, payload}`，每条流的首个 item 是全量 baseline 或 snapshot（[Connection README](../packages/client/connection/README.zh.md)）。
- 时序图：[agent-lifecycle](../docs/agent-lifecycle.zh.md)。

### 第 1 级：一条消息的旅程（对应上面的主线）

| 课 | 操作 | 要回答的问题 | 去哪看 | 结论 |
|---|---|---|---|---|
| 1.1 | 发一句"你好" | `POST /api/session/prompt` 的请求体长什么样？回答又从哪条 WS 流回来？ | ① ② ③ | **发出走 HTTP，回答走 WS，两边靠 `requestId` 对上。** ① 点发送时浏览器先生成 `requestId`（[client/sessions/session.ts](../packages/api/session-controller/src/client/sessions/session.ts) `beginSubmission`），再 `POST /api/session/prompt`，外层信封是 `{type, rpcId, method, payload.args.request}`。② `request` 有 5 个字段：`requestId`；`sessionId`；`mode`（`queue` 自成新一轮，`steer` 在当前轮下一个 step 边界并入，不打断正在进行的调用）；`content`（数组，可混 text/image/file，空数组表示让失败停下的会话继续）；`clientTimeZone`（写进消息来源，供时间上下文告诉模型用户那边几点）。**两个 ID 分两层**：外层 `rpcId` 管这一次网络调用；里层 `requestId` 管"用户发的这一条消息"，Host 把它记进日志的 `source.rpcId`，同一个 ID 再来就直接回 `accepted`、不重复入队（[commands.ts](../packages/api/session-controller/src/commands.ts) `hasPromptRequest`）。所以它必须由会重发的浏览器事先生成。③ HTTP 只回 `{accepted:true}`。回答由 Host 推到早已打开的 WS `session/follow` 流上。Host 就是 `dsh web` 起的那个 Node 进程，持有到 DeepSeek 的 SSE、写会话日志、生产各条流（[web-client](../docs/subsystems/web-client.zh.md) 的分层表）。浏览器判断"已收下"看哪路先到：HTTP 回执，或 follow 流里出现带自己 `requestId` 的 Inbox 行（[ui-conversation service.ts](../packages/client/ui-conversation/src/client/service.ts)）。浏览器不自动重发；手动再点一次会生成新 ID，模型会回答两次。 |
| 1.2 | 看会话 jsonl | 一轮对话写了哪些事件，顺序是什么？ | [session](../docs/subsystems/session.zh.md)、主线 ④ | **一轮（turn）= 多步（step），每步一次模型调用，每步结束就落盘。** 顺序：`agent/inbox/spliced`（消息进 inbox）→ `turn/start` → `step/start` → 本步要给模型的消息 → `assistant/message`（成品 `message` + 逐帧录像 `stream`）→ 有工具调用就 `tool/call` → `tool/result` → `step/end`，下一步再来；某步只回文字不调工具，就 `turn/end`（`completed` / `aborted`）。**第一步的消息顺序**：`system/message` → 用户原文（`source.rpcId` 就是 1.1 的 `requestId`）→ 上下文 `user/message`：`agent-instructions`（`~/.agents/AGENTS.md` 等）、`runtime-context`（工作目录、沙箱、GUI 地址）、`skill-catalog`（装了哪些 skill）、`time-context`（时间、时区、间隔）。这些都是快照：第 1 轮全量写，之后只在内容变了才追加新的一条，旧的不改（AGENTS.md 每步比对 SHA-1，变了追加 `replace`，[agent-instructions](../packages/context/agent-instructions/src/state.ts)）；时间每轮都变，所以每轮都有。**为什么写进日志**：模型看到的东西都能从日志重建（重放、恢复、fork），且旧消息不变让请求前缀稳定、命中缓存。**Ctrl+C 停 Host** 是正常退出：被打断那步写成 `interrupted: true` 的 `assistant/message`，再写 `turn/end {aborted: disposed}`，界面显示"已停止"；之前各步的工具效果（写文件、交付）早已落盘不受影响；重启加载时追加 `session/end-seed` 分隔历史与新内容。 |
| 1.3 | 看思考和正文逐字出现 | SSE 一帧怎么变成屏幕上的一个字？ | ⑤ ⑥ ⑦ ⑩，[llm-streaming](../docs/subsystems/llm-streaming.zh.md) | **到一帧推一帧，不等整步结束；一步结束才落盘。** 路线：DeepSeek 发 SSE 字节流 → Host 的 llm-deepseek 解析器把字节切成 SSE 帧、翻译成统一的 `StreamChunk`（`reasoning-delta` / `text-delta` …，[sse.ts](../packages/llm/llm-deepseek/src/sse.ts)）→ agent loop `for await` 每个 chunk，`live.push(chunk)` 发出 `agent/assistant-stream` 事件、`revision` +1（[agent.ts](../packages/core/agent-loop/src/agent.ts)）→ session-controller 同时做两件事：a. 累积进内存，留作重连快照；b. 推给每个已连接的浏览器（[history/assistant-stream.ts](../packages/api/session-controller/src/history/assistant-stream.ts)）→ WS `session/follow` → 浏览器 `acceptFrame` → React 渲染。**一根流上有两类条目**：`assistant-stream` 是模型正在说的草稿，思考和正文都算，只在 Host 内存里，按 `revision` 编号（每个 Agent 一个计数器，跨 step 一直加，Host 重启后清零）；`event` 是已提交、写进 jsonl 的事件，按 `seq` 编号。草稿的 `start` 帧带 `startedAfterSeq`，标明它接在哪条已提交事件之后。一步结束时草稿才变成 `assistant/message` 落盘，`stream` 字段就是这份逐帧录像。**漏帧**：浏览器发现 `revision` 不连续，就当线路故障处理，自动重连，首帧是带草稿底稿的 snapshot，已显示的内容保留（[transport.ts](../packages/api/session-controller/src/client/transport.ts)）；Host 的累积器发现跳号，就丢掉这次的半截草稿，只对齐编号（[assistant-stream.ts](../packages/api/session-controller/src/assistant-stream.ts)）。原则是宁可不给，也不给错，最终以落盘版本为准。 |
| 1.4 | 回答到一半点停止 | 取消信号怎么从按钮传到 fetch？日志里留下了什么？ | service.ts `cancel`、`assistant/attempt` | **停止就是掐断那一个 AbortSignal：fetch 断了，已收到的部分照样落盘。** 路线：点停止 → `conversation.cancel()`（[service.ts](../packages/client/ui-conversation/src/client/service.ts)）→ `POST /api/session/cancel`，请求体只有 `sessionId`，因为"停下"做几次都一样，不需要 1.1 那种去重用的 `requestId` → Host `commands.cancel` 调 `agent.cancel({kind:'user'}, {keepInbox:true})`（[commands.ts](../packages/api/session-controller/src/commands.ts)），只停当前这一轮，排队的消息保留 → Agent `phase.abort.abort(cause)`（[agent.ts](../packages/core/agent-loop/src/agent.ts)）。这个 signal 在开工时就传给了 llm-deepseek 的请求和 agent loop 的 `for await`，所以 fetch 被掐断，循环抛出异常进入 catch。**落盘看这次模型调用已经收到了什么**：收到过思考或正文块，就写一条带 `interrupted: true` 的 `assistant/message`，只有思考也算；第一块还没到（发送后约 0.2 秒内）就停了，只写 `assistant/attempt`（只有逐帧记录，没有成品）。之后写 `step/end`、`turn/end {aborted: {kind: user}}`。**和 Ctrl+C 是同一套机制**：同样的 abort，同样写半截消息，只是原因记成 `disposed`，而且 Host 进程退出，重启时追加 `session/end-seed`。**半截回答下一轮模型看得到**：每步都从日志重建上下文，`interrupted` 的 `assistant/message` 在历史里，所以发"继续"时模型能引用断掉的那句接着写；`assistant/attempt` 不进上下文。 |
| 1.5 | 刷新页面 | 刷新后历史怎么恢复成一模一样？ | follow 首帧 baseline，[Web Client](../docs/subsystems/web-client.zh.md) 的"重连" | |
